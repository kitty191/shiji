## 2. 发现

### F01（P2，审查时为代码路径风险；已修复）：结算被交易操作锁住后可能不自动预览

`CheckoutPage.tsx` 的预览 effect 在 `blocked` 为真时直接返回，但依赖只有 `key`、`reload`、`addressBusy`。如果首次进入结算时恰好有全局交易操作在途或结果待确认，地址已就绪、地址和选择未改变，随后操作解除锁定不会重新触发预览。页面继续显示“正在核对结算内容…”，提交不可用；手动点“刷新地址与预览”可恢复。建议将阻塞状态纳入 effect 生命周期，并验证在途→明确失败/恢复后的重新预览；同时防止解除锁定前的旧请求覆盖新预览。本轮没有注入慢请求/未知响应进行浏览器复现，按代码确定的状态组合记录，不写成已执行的端到端复现。

### F02（P2，审查时为代码与样式风险；已修复）：购物车和交易恢复提示占用同一位置

`CartUndoNotice` 与 `TransactionRecovery` 都渲染为 `.cart-undo-notice`，CSS 使用相同的固定左下角位置、宽度和 `z-index: 8`。两者可并存：购物车删除后的 8 秒撤销提示由外层 CartProvider 保留，结算/付款/发货/收货结果未知时内层 CommerceProvider 同时显示交易确认提示。后渲染的购物车提示会盖住交易确认入口。建议为两类提示安排独立堆叠位置或统一提示容器，并验证窄视口与键盘可达。此轮未注入故障让两条提示同时出现在生产浏览器。

### F03（P3，审查时浏览器已复现；已修复）：越界页码被误报为空数据

本机已有 23 笔买家店铺订单时，访问 `#/orders?page=999`，页面显示“还没有订单”“去逛逛”，同时仍给出“上一页”；实际只是当前页没有记录。商品首页有 9 件商品时，访问 `#/buyer?page=999` 也显示“暂时没有符合条件的商品”，并建议清空筛选，实际无筛选且只是页码越界。商家订单页已按 `page.total > 0` 区分“当前页没有本店订单”，可沿用同一判断。建议保留分页返回入口并给出准确空态，不把已存在的数据说成零条或筛选无匹配。

## 4. 2026-10-26 F01/F02 后续修复（第一小批）

- F01：结算预览 effect 将 `blocked` 纳入依赖，只在原预览缺失/未完成时于解锁后自动重启；已有报价提交失败时保留人工复核状态，不因解锁自动清除。首次进页遇全局交易锁定时显示等待说明；旧请求在锁定状态变化时清理，不覆盖新结果。隔离浏览器样本验证进入结算时交易在途、地址随后就绪，再以明确失败解除锁定，观察到等待说明→自动预览→59 元报价及可提交状态；另注入 `PRICE_CHANGED`，观察到提交仍禁用且保留“请重新预览”，手动刷新后才恢复。故障样本只存在临时构建副本，已恢复为正式源码。
- F02：交易提示和购物车撤销提示改由同一 `global-notices` 容器依次排列，容器限制视口高度并允许内部滚动；单条提示仍保持原左下角位置。隔离浏览器样本在 1280×720 和 800×600 同时显示两条提示，矩形不重叠、无水平溢出；临时假购物车提示已从构建副本恢复。正式模拟购物车单项删除后，真实 8 秒撤销提示仍出现并可操作。
- 本小批 213 项现有测试通过，TypeScript、mock/API 生产构建通过；未新增模拟 JSX 的单元测试。F03 仍待下一小批。README 功能说明、OpenAPI、旧 HTML 原型、真实后端和依赖未变。
