1. **核心数据库模型**：先绘制 ER 图，明确用户与店铺成员关系、商品与 SKU、支付单与店铺订单、订单快照、库存占用的关系、关键字段、状态及核心约束。复用现有业务规则，未确认项单列；这一阶段不必冻结所有物理字段、索引或生成 DDL。
2. **页面与操作清单**：逐页核对展示数据、用户动作、权限和异常，形成“页面/动作 → 接口 → 相关实体”的对应关系，覆盖买家、商家与平台，降低接口遗漏。接口由业务能力和页面需要决定，不按表机械生成 CRUD。
3. **接口与表结构联合细化**：定义请求、响应、错误码、筛选分页、金额/时间及写操作幂等；同时补齐字段字典、类型、主外键、唯一约束、索引、库存并发和事务边界。用跨店结算、价格变化、库存不足、重复付款和超时关闭相互校对；数据库产品与持久化工具仍待工程选型确认。
4. **建立 v0.1 设计基线**：在首版范围内完成接口清单和数据库设计评审，之后再按模块实现。草案阶段集中修订；基线形成后区分需求新增、设计遗漏与实现修正，记录变更原因和前后端影响。兼容性新增不自动要求切换 API 大版本，破坏性变更另行评估。

先做数据库核心设计能减少关系、状态与约束遗漏，但无法保证以后不新增接口；新的业务操作和设计遗漏仍可能产生契约变化。API 与表结构保持不同职责，返回业务需要的数据，不直接暴露数据库整行，内部索引调整等实现变化不应强迫接口修改。稳定契约继续供后续 Python 版复用。当前已生成 OpenAPI 草案，未生成 DDL 或创建数据库；Agent 仍仅预留商城查询边界。

## 6. 主演示脚本

1. 普通账号登录买家商城，从头像进入商家中心，查看权益和流程、提交申请，再由平台管理员审批。
2. 商家创建带规格的商品，设置价格库存并上架。
3. 买家通过关键词、分类、价格筛选和排序找到商品，查看详情并选择规格。
4. 买家从两家店选择三个 SKU 加入购物车，进入结算。
5. 提交后展示一个支付单和两个店铺订单，完成模拟付款。
6. 两家店的商家分别查看本店订单并发货；买家分别确认收货。
7. 平台查询支付单及对应店铺订单，展示订单状态和处理记录。
8. 补充展示库存不足、价格变化或模拟付款失败，说明怎样修改条件或重试。

目标是用一条连续流程呈现产品体验、数据建模、权限与交易规则。Agent 不属于当前主演示脚本。

## 7. 交易与权限验收

以下为正式工程待执行的验收要求；D055 / D057 / D058 / D059 / D062 等新增规则目前仅完成设计文档同步，未执行本轮浏览器或后端验收。推荐策略已确认，具体参数和性能/效果指标随工程数据细化，不预先承诺准确率。

| 场景 | 预期结果 |
| --- | --- |
| D062：同组合多代再售 | 停用 A 后同组合创建 B、ID 不同，旧购物车仍不可购买；再创建同时启用的 C 冲突。并发至多一个新启用组合，旧占用/成交引用不迁移；库存为零补货仍用原 ID |
| D062：购物车快速连点 | 同 item_id 最多一个请求在途，合并最新目标并用确认数量发下一次；超时原键恢复、跨页面真实冲突不覆盖，其他商品项可独立处理 |
| D062：无引用素材回收 | 超过宽限期且无任何受保护引用才可回收；头像、申请快照、草稿/下架及订单任一引用阻止删除；绑定与清理竞争不误删，删除失败可追踪重试 |
| D062：编辑中 401 | 原账号重新认证后当前内存表单保留，重检权限/编辑冲突后由用户继续；换账号清除私有输入，不自动重放购买，刷新只承诺已保存草稿回显 |
| 跨两家店提交结算 | 生成一个支付单、两个店铺订单，金额与明细一致 |
| 同时购买最后一件 SKU | 只有符合库存条件的请求成功，库存不为负 |
| 某个 SKU 库存不足 | 整次结算失败，不残留部分订单或占用 |
| 提交时商品价格变化 | 返回新报价并要求重新确认，不静默涨价成交 |
| 重复提交同一幂等请求 | 返回原结算结果，不重复建单 |
| 同一幂等键更换商品或数量 | 拒绝为冲突请求 |
| 重复模拟支付事件 | 订单与库存仅确认一次 |
| 重复取消或超时扫描 | 库存仅释放一次，支付单保持已关闭 |
| 支付与超时关闭同时发生 | 只有一个合法转换成功，订单与库存结果一致 |
| 已付款后重复取消 | 按首版规则拒绝，不释放已售库存 |
| 修改商品和收货地址 | 既有订单仍显示下单时的快照 |
| 商家访问其他店铺的商品或订单 | 服务端拒绝，不能通过修改 URL 或参数绕过 |
| 买家访问他人的订单与地址 | 服务端拒绝 |
| 店铺停用或商品下架 | 禁止新结算，已有待支付单可在截止时间前支付，历史订单仍可查看和履约 |
| 商家自主下架商品后的购物车与详情 | 购物车显示商品已下架且不可结算；点击进入最小下架状态页，下方展示其他商品推荐，不能继续购买原商品；草稿/平台限制/店铺停用不借此公开 |
| 首页规则推荐与轮换 | 按配置规则混合新品/精选/分类并适当打散店铺；相近候选少量轮换，翻页和详情返回保持顺序，不重复凑数，不覆盖用户明确选择的价格/上新排序 |
| 下架页替代推荐 | 排除原商品及无货/下架/受限/停用店铺候选，优先本店同类近价商品，不足再从全站同类补齐；仍不足少展示，价格按 D060，近价自填价分支随 P035 确定，查询不占库存 |
| 商家调整库存或停用 SKU | 不覆盖已占用数量，不删除历史订单引用的数据 |
| 商家用新规格替换旧规格 | 一次保存停用并保留旧 SKU、为新组合创建新 SKU；原购物车保留原选择，提示所选商品不能购买、商品图变灰且不可勾选结算，点击进入原店铺，不自动换新规格；新规格补库存不恢复旧规格购买能力 |
| 启用 SKU 库存为零 | 显示已售罄并禁止购买，与被替换而停用的规格失效提示区分 |
| 不完整商品草稿保存后重新进入 | 回显已保存文本、图片顺序及已填写规格/价格/库存，继续保存更新同一商品 ID；草稿不对买家公开 |
| 草稿发布缺少必要内容 | 拒绝发布并指出缺项，已保存草稿不丢失，不伪造零元 SKU |
| SKU 绑定图片或未绑定 | 使用同商品的有效图片，未绑定或失效时回退主图，拒绝跨商品越权关联 |
| 旧表单改库存与下单同时发生 | 按冲突规则处理，不覆盖期间的交易变更；成功人工调整保留前后数量、原因、操作者和时间 |
| 编辑、改价及重新上架 | 首次发布时间保持不变，上新排序按首次发布时间 |
| 关单 worker 重启 | 继续处理数据库中的过期订单，结果幂等 |

库存竞争、付款幂等、状态转换和资源权限适合针对性自动化测试；端到端验证主购买流程。页面文案或轻量样式调整使用人工检查即可。

## 8. 后续 Agent 评估（暂缓）

本节保留未来候选方案，不属于首版验收，也不在当前准备模型或评估数据。用户后续启用 Agent 时，可从 30 条固定场景开始：

| 分类 | 数量 | 关注点 |
| --- | --- | --- |
| 正常导购 | 12 | 预算、分类、用途、规格和多轮修改 |
| 空结果与矛盾条件 | 4 | 不虚构商品，能解释筛选限制 |
| 模型/工具故障 | 4 | 超时、错误、终止与普通搜索退路 |
| 权限与恶意内容 | 6 | 商品文本注入、越权指令、试图付款或改价 |
| 信息变化 | 4 | 价格、库存、下架与推荐事实一致 |

逐条检查任务是否完成、推荐商品是否真实、是否满足可验证约束、工具参数是否正确、是否出现未经授权的写入。延迟、token 与成本在实际接入后测量，不提前宣称达标。

后续 Agent 阶段的候选验收要求：所有商品卡片可溯源；固定权限用例均被业务代码正确阻止；失败场景有反馈；至少真实接入一次模型并保存脱敏运行证据。该要求已由 D037 移出商城首版验收。
关键不变量出现一次失败就应修复后回归。导购质量分数与性能目标在拿到首批基线后设定，评估结果与提示词版本一起保存。

### 桌面布局与入口验收补充

- 展开工具栏时保持已认可的商品间距；收起后横幅、分类和商品网格向右补齐；再展开恢复原间距。刷新恢复收起状态时布局也应正确。
- 普通注册登录进入买家商城或先前的有效购物上下文；不要求普通用户选择商家身份登录。
- 同一“商家中心”入口按未申请、草稿、待审核、驳回、已开店分别进入介绍、续填、进度、修改与工作台。
- 驳回需要原因；未经审核不能获得发布权限。顶部原型场景切换不能作为正式权限机制。
- 商品详情在桌面保持左侧缩略图、中间大图、右侧购买信息；切图与切规格各自生效，售罄状态禁用购买。
- 价格区间与关键词、分类和排序组合；改变条件回第一页，详情返回保留原页。正式服务端重新校验参数、页码和报价。
- 独立浏览器的后退、前进和刷新恢复当前页面及条件；未保存编辑的离开提示不丢失继续编辑的输入，不能把地址中的订单号当作访问权限。
- 批量上下架逐件校验店铺归属和业务状态，清楚展示未处理项，不能因为其中一项受限而静默改变其状态。
- 桌面内容最大 1280 px 居中，常用桌面保持四列；筛选和排序随空间换行，计数靠近排序。商品默认方图、标题最多两行且可键盘进入详情；焦点在实际外观下清晰可见，价格口径可访问，空错误区不占位。原型检查不替代正式前端验收。

## 10. Python 迁移验收

在 Java 版稳定后执行；优先在隔离演示数据库中对照，而非让两套后端同时写入。

- 使用同一套种子数据和接口请求集，验证响应结构、金额、状态、错误码、分页与认证行为。
- 重新演示“商品上架 → 跨两店结算 → 一个支付单、两个订单 → 模拟付款 → 分别发货和收货”。
- 验证库存竞争、幂等提交、重复付款、取消与关单竞争、商家及买家数据隔离。
- 前端不依赖 Java 类名或异常堆栈；若迁移时已启用 Agent，再验证工具与流式事件兼容，不把 Agent 作为迁移前置条件。
- 数据结构由一套有效迁移链管理；切换时停用旧版的写接口、关单任务与消费者，再交接给新版。

迁移进度不影响先交付 Java 版；首版不提前创建 Python 商城项目。
