## 2. 通用约定

### 2.1 路径、类型与字段

- 基础路径 `/api/v1`；下文所有路径均包含该前缀，属于设计标识，当前不能直接请求。
- JSON 字段使用 `snake_case`。实体 ID 是不透明字符串；金额为整数分、币种 `CNY`，`5900` 表示 59 元。数量为正整数；库存为非负整数。
- 时间使用带时区的 ISO 8601，例如 `2026-10-19T08:00:00Z`。时间、操作者、归属、价格汇总和状态由服务端确定。
- 普通请求使用 `application/json`，图片上传使用 `multipart/form-data`。图片 URL 为服务端生成的展示地址，持久引用仍使用 `asset_id`，不把短期签名 URL 当永久图片标识。
- 未声明的写入字段建议返回 `400 / INVALID_ARGUMENT`。注册不接受 `roles`，个人资料不接受 `status`，购物车不接受用户归属、商品价格或店铺归属等额外字段。
- `POST` 创建资源成功用 `201`；查询、修改和业务动作成功用 `200`。删除也用 `200` 返回结果，便于说明购物车撤销等状态。复用幂等创建结果时沿用首次成功状态码。

### 2.2 成功、失败与列表

D066：所有 HTTP 响应统一为 `Result<T> = {code,message,data,request_id}`。成功 `code=SUCCESS`、data 为业务数据；失败使用具体结果码、data 固定为 null，按需补充 field_errors/details。后端统一通过 `Result.success(data)`、`Result.fail(ResultCode.NOT_FOUND)` 等工厂方法构造；异常交给统一异常处理，业务代码不直接返回一句字符串或随手拼写错误码。本轮仅确认契约，尚未创建 Java 类。

结果码在后端用 `ResultCode` 枚举定义，JSON 以枚举名称字符串传输，例如 `"code":"NOT_FOUND"`；不传枚举序号。前端按 code 处理逻辑，message 为统一文案/安全上下文提示，不能据中文 message 判断状态。商品名、地址等业务文本仍正常使用字符串。OpenAPI 的 ResultCode 是完整目录，ErrorCode 为失败子集；HTTP 200/201、400/401/403/404/409 等继续表达真实请求结果。

```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {
    "user_id": "user_demo",
    "nickname": "拾光同学"
  },
  "request_id": "request_demo_me"
}
```

```json
{
  "code": "INVALID_ARGUMENT",
  "message": "最高价格不能低于最低价格。",
  "data": null,
  "request_id": "request_demo_error",
  "field_errors": [
    {
      "field": "max_price",
      "code": "INVALID_RANGE",
      "message": "请检查价格区间。"
    }
  ],
  "details": null
}
```

失败响应的 `field_errors`、`details` 均可省略；如提供，field_errors 为数组，非字段错误可为空数组，details 为业务错误规定的安全数据或 null。不得透出 SQL、密码、令牌、其他用户资料或平台内部限制原因。

顶层不再套 error 对象，替换旧版成功/失败两种外壳。批量部分失败时，HTTP 外层仍为 Result，data 内逐项 error 沿用 `Error = {code:ErrorCode,message,field_errors,details}`；单项错误不另加 request_id。FieldError 的 code 使用 FieldErrorCode 枚举，field 使用请求字段路径，例如 items[0].quantity。request_id 只表示本次 HTTP 请求，幂等重放也生成本次追踪 ID，不作为业务防重键。

分页对象 `Page<T>`：`items: T[]`、`page: integer`、`page_size: integer`、`total: integer`、`has_more: boolean`。`page` 从 1 开始；`page_size` 默认 12、上限 50。空结果和超出最后一页均返回空数组，不暗中跳回第一页。首页虽然接口返回 `total`，页面仍按 D047 不显示商品总数；本店结果数可以展示。

公开商品流额外返回可空 `feed_token`：需要翻页/返回定位时，默认或显式排序首次查询都建立有序候选 ID 上下文，绑定筛选、排序和 page_size，后续页复用；改变条件或 page_size 后重新开始。仅有固定随机种子或次级 ID 不能在数据变化时保证不重不漏。实现可以使用有签名的上下文或有限期结果集，存储方式和期限待选，不新建行为喜好表。显式价格/上新排序优先，使用稳定 ID 作同值次级排序。

v0.2 候选失效策略：新上架商品等新增候选在主动刷新后进入；已纳入上下文的项若变为不可见，或改价/库存变化使原筛选资格或明确价格排序失效，则返回 `409 / FEED_EXPIRED`，保留筛选请用户刷新，不跳过后再按当前 OFFSET 补位造成重复。有效上下文的 total 为该上下文候选总数，不宣称实时全站总数；过期不返回旧的不可见数据。商品卡仍读取当前有效报价，商品流不预留库存。具体结果集保存和校验成本留到工程选择，不能把一个不保存候选序列的 seed 当成已经解决问题。

### 2.3 身份与权限

认证方式尚待选择，本文用“当前身份”表示已验证会话；不同时规定 Cookie 和 JWT 两套方案，也不提前定义刷新令牌接口。选定后补请求头/Cookie、安全属性、会话期限、退出失效和相应防护。

接口表权限缩写：`公开` = 无需登录；`用户` = 当前有效账号；`申请人` = 本人申请；`店主` = 当前用户有对应店铺成员权限；`管理员` = 有效平台角色。店主不代表管理员，停用店铺仍保留店主归属。

私有接口不接受客户端 `user_id` 指定归属。买家订单通过 `shop_orders → payment_groups.buyer_user_id` 校验；商家订单通过 `shop_orders.store_id → store_members` 校验。访问别人的私有对象建议返回统一 `404 / NOT_FOUND`；已登录但没有分区角色时返回 `403 / FORBIDDEN`。

停用店铺允许店主查看限制原因、已有订单和完成合法履约；不允许新发布、上架或供给编辑等经营写入。具体哪些只读资料保留，由商家接口白名单控制；不能通过“店铺停用”导致已有买家订单无法发货。账号本身失效时仍须拒绝认证/写入。

### 2.4 幂等与编辑冲突

接口表“防重”为 `K` 时，请求必须携带 `Idempotency-Key`（不透明字符串，长度等格式随工程确定）。防重范围为当前调用者＋具体业务操作及目标＋键；相同键和相同请求返回原结果，不重复产生业务效果，同键不同请求返回 `409 / IDEMPOTENCY_CONFLICT`。处理中重试返回 `409 / REQUEST_IN_PROGRESS`，客户端稍后使用原键重试；未获得确定结果时不能换键盲目提交。

处理顺序先核验当前认证与资源访问权限，再查询该调用者的幂等结果；已撤销的权限不能借历史结果恢复访问。命中已完成请求后，旧 edit_token、旧状态或预览到期不再导致重复执行。重放中的资源 ID/首次业务结果可能携带旧状态，前端应通过对应 GET 重新读取当前付款/订单状态，不能拿首次 PENDING 响应重新启用已经付款的操作。

普通字段/业务校验失败不消耗一次性业务资格，修正请求使用新键；结果不确定的超时须用原键查询/重试。暂存 PROCESSING 的记录要有明确的失败恢复/接管机制：事务回滚后可重试，原业务已提交但响应丢失时能恢复原结果，不能无限返回 REQUEST_IN_PROGRESS。若批量任务逐件事务，父请求接管还须依据逐件结果继续未处理项，不能重新执行已完成项；最终数据库/租约实现待选。

下单、模拟付款、取消、审核、发货、收货、库存调整等按对应权限和合法状态转换执行。新请求也不能突破状态限制；幂等记录不是唯一防线，库存占用、事件及业务记录还须有唯一约束/条件更新。防重记录保留期和清理策略待定。

可修改资源返回不透明 `edit_token`；修改请求提交读到的旧值。它用于识别过期表单，冲突返回 `409 / EDIT_CONFLICT` 并要求重新加载；不指定必须新增数据库版本列。商品编辑令牌覆盖共享内容、规格、价格及状态，库存独立读取/调整，不能因保存商品表单覆盖期间发生的库存变化。草稿、商品与库存的最终并发落地仍待工程细化。

### 2.5 错误码

| HTTP | 业务码 | 使用场景 |
| --- | --- | --- |
| 400 | `INVALID_ARGUMENT` | 参数格式、价格区间、重复 SKU、空批量请求等不合法 |
| 401 | `UNAUTHENTICATED`、`INVALID_CREDENTIALS` | 需要登录或账号密码校验失败；登录失败不区分账号不存在和密码错误 |
| 403 | `FORBIDDEN`、`STORE_DISABLED` | 无分区权限或停用店铺发起受限经营操作 |
| 404 | `NOT_FOUND` | 不存在、公开不可见或不属于当前账号/店铺的对象 |
| 409 | `LOGIN_NAME_TAKEN`、`APPLICATION_EXISTS`、`STORE_LIMIT_REACHED` | 登录名冲突、重复有效申请或超过单店限制 |
| 409 | `INVALID_STATE`、`EDIT_CONFLICT`、`SKU_COMBINATION_CONFLICT` | 状态不允许、旧表单或规格组合冲突 |
| 409 | `ITEM_NOT_PURCHASABLE`、`INSUFFICIENT_STOCK` | 当前选择失效、下架、不可购买或库存不足 |
| 409 | `PRICE_CHANGED`、`ADDRESS_CHANGED`、`CART_CHANGED` | 预览后价格、收货内容或选中购物车项变化，需要重新预览 |
| 409 | `PREVIEW_EXPIRED`、`PAYMENT_EXPIRED`、`RESTORE_EXPIRED`、`FEED_EXPIRED` | 结算预览、付款、撤销或商品流上下文到期 |
| 409 | `IDEMPOTENCY_CONFLICT`、`REQUEST_IN_PROGRESS` | 防重键复用冲突或原请求还在处理 |
| 413 / 415 | `FILE_TOO_LARGE` / `UNSUPPORTED_MEDIA_TYPE` | 文件大小超限或文件类型不允许 |
| 429 / 503 | `RATE_LIMITED` / `SERVICE_UNAVAILABLE` | 频率限制或暂不可用；具体阈值、重试策略待实施 |
| 500 | `INTERNAL_ERROR` | 未预期服务错误；响应只给安全说明和本次 request_id，不返回内部异常栈 |

公开 SKU 批量查询对不可见项只返回 `NOT_AVAILABLE`；不得用内部错误码泄露原因。私有购物车可按授权返回 D057 / D058 的具体失效文案和安全跳转目标。

## 3. 账号与个人资料

| 编号 | 方法与路径 | 权限 / 防重 | 请求字段 | 成功数据 | 主要表 |
| --- | --- | --- | --- | --- | --- |
| A01 | `POST /api/v1/auth/register` | 公开 / — | `login_name, password, nickname?` | `AuthResult`，201 | `users`；会话存储待选 |
| A02 | `POST /api/v1/auth/login` | 公开 / — | `login_name, password` | `AuthResult` | `users, user_roles, roles, store_members, stores` |
| A03 | `POST /api/v1/auth/logout` | 当前会话 / — | 空对象 | `{logged_out:true}`；清除/失效当前会话 | 会话存储待选 |
| A04 | `GET /api/v1/me` | 用户 / — | 无 | `CurrentUser` | `users, user_roles, roles, store_members, stores, media_assets` |
| A05 | `PATCH /api/v1/me` | 用户 / — | `nickname?, avatar_asset_id?, edit_token` | `CurrentUser` | `users, media_assets` |

注册采用账号密码，昵称可选，默认昵称/头像由系统产生；注册成功进入登录态。确认密码由前端比对，不要求在网络中重复传输密码。账号长度、密码策略及昵称长度未最终选定，后续作为统一参数表补齐；首版登录名只读。注册仅创建用户及所需会话，不创建购物车、店铺、申请、地址或订单。

登录名大小写/空白归一和唯一查重必须使用同一规则，具体规则待确认；不能在注册和登录中各采用一套归一方式。

`avatar_asset_id:null` 表示恢复内置默认头像；省略表示保留。昵称不能通过 `null` 清空。公开注册/资料接口不能写入平台角色。头像须是当前用户可绑定的可用素材。

`AuthResult = {user: CurrentUser, session_expires_at: datetime}`，具体凭证通过何种通道交付由认证方案补齐；不在此承诺一定在 JSON 中返回 token。登录后的站内回跳由前端保留并校验目标：普通登录默认买家首页，管理入口认证后仍要验证 `platform_roles`。`logout` 清理当前会话，已过期会话重复退出同样可完成清理；“退出全部设备”不属于本稿。

D062 确认 401 当前表单保护：受保护请求返回 401 时暂停写入，保留当前账号所属的页面内存编辑值、商品/申请 ID、临时关联键及已上传素材 ID，不立即清空表单或强制完整刷新页面。复用 A02/共用登录流程恢复认证；多个同时失败请求合并为一次登录引导，不各自跳转清空状态。密码、会话凭证不存进恢复表单。

只有恢复为原 user_id 才能继续原表单；换账号、主动退出或离开时清理原账号私有内存。重新登录后先读取身份、资源权限及最新编辑/库存状态；不能把新 edit_token 直接套在旧表单上静默覆盖别人修改，也不自动重放下单/付款。未确定是否已成功的写请求按原幂等键/资源查询恢复结果，确认未生效后再由用户继续。素材已不可用时保留其余输入并提示重新选择。

本规则只保护当前前端运行会话中的内存输入；不承诺浏览器刷新、关闭、崩溃或跨设备恢复未保存表单。已保存草稿仍由服务端回显。续期/refresh、会话技术和具体期限继续待选，不能将“本次输入保留”解释为新增双令牌或忽略权限撤销。

G01 支持草稿、在售、下架筛选；平台限制单独返回，不让商家用修改销售状态覆盖。G02 仅在主动创建商品时执行，刷新编辑页不再创建。G03 按服务端已保存商品回显，不承诺未保存输入跨刷新/关闭恢复；当前运行页面内遇到 401 的内存保护按 D062。零库存不禁止完成有效商品发布，但发布后须表达售罄；无有效 SKU 不能发布。

G04 一次事务处理共享资料、图集、规格、SKU 更新及替换。请求中不含的部分保留；`fields.display_price_override:null` 表示清空自填价恢复自动计算。`images:[]` 可清空草稿图集，但在售商品不能通过编辑绕过发布完整性要求。在售商品保存后的最终结果仍须具备合法购买结构，否则整次返回错误。

已存在的 SKU 的规格组合不可改成另一组合：保持原 `sku_id` 只允许改当前售价、绑定图等可变资料；替换必须显式提交 `disable_sku_ids` 并创建新 SKU，旧 SKU 留存。旧规格选项含义不能被改写影响历史选择。

D062 已确认同组合再售：历史停用 SKU 不阻止商家新建相同规范组合的新 SKU ID，原 SKU 继续停用；仅当同一商品中已有另一个启用的相同完整组合时返回 SKU_COMBINATION_CONFLICT。同请求中停用旧 SKU 并建立新 SKU，一次事务提交；并发请求也须保证同时启用组合至多一条。请求中复用合法的旧规格值 ID 可以表达同组合，不需要改名规避冲突；新建仍不传旧 sku_id，采用 client_key 获取新 ID。

再售不继承旧 SKU 的库存占用或自动复制可售库存/售价，由商家按新 SKU 确认；老购物车/历史订单引用仍是老 SKU，不能自动改绑或恢复原选择购买能力。旧订单已有占用仍按原订单付款/关闭规则处理。临时断货只需把原 SKU 可售库存设为 0，补货继续使用原 SKU，与退役组合再售区分。

G04 对已有 SKU 不接受库存值；新 SKU 的 `initial_available_stock` 为可选非负整数，本版候选在创建 SKU 时同时初始化一行库存，未填取 0。这样已保存的 SKU 都能通过 G08/G09 继续调库存，不会出现“已有 SKU 禁止初始化、库存接口又没有令牌”的死路。未创建 SKU 的空草稿仍可没有库存。人工调整独立走 G09，用独立令牌防止旧表单覆盖新库存。初始化是否另记为人工调整记录尚待物理设计，不能伪造“调整前库存”记录。

建议 `ProductEditRequest`：

| 字段 | 类型 / 条件 | 含义 |
| --- | --- | --- |
| `edit_token` | string，必填 | G03/G04 返回的商品编辑令牌 |
| `fields` | object，可省略 | `title?, category_id?, description?, attributes?, display_price_override?`；不接受 store_id、平台限制或 published_at |
| `images` | `ImageEdit[]`，可省略 | 给出本次完整展示图集及顺序；省略保留，数组首图为主图 |
| `dimensions` | `DimensionEdit[]`，可省略 | 提供时为完整的当前编辑维度/选项定义，最多两个当前维度；省略保留。被移出的历史定义仅归档，不改写旧 SKU 引用 |
| `skus` | `SkuEdit[]`，可省略 | 新建/修改的 SKU；省略某旧 SKU 不自动停用，须用下一字段明确表达 |
| `disable_sku_ids` | string[]，可省略 | 本商品需要停用的旧 SKU，数组内不可重复 |

嵌套编辑字段：

- `ImageEdit = {product_image_id?:string, client_key?:string, asset_id:string}`。旧图使用 ID，新图使用仅本请求有效的 `client_key`；移除展示图时在同一事务处理 SKU 图绑定回退，不删除已用素材对象。
- `DimensionEdit = {dimension_id?:string, client_key?:string, name:string, values:ValueEdit[]}`；`ValueEdit = {value_id?:string, client_key?:string, value:string}`。数组顺序表达展示顺序。旧项用 ID，新项用本请求唯一临时键。
- `SkuEdit = {sku_id?:string, client_key?:string, spec_values:SpecSelection[], price:integer或null, image_ref?:EditRef或null, initial_available_stock?:integer}`。尚未首次发布的商品草稿允许 SKU 的价格为 null，包括此前已保存、仍未补完的旧草稿 SKU；不能要求商家填写价格后才允许保存其他内容。发布及已发布商品的有效 SKU 必须正价，不能把历史有效售价改为空。已有 SKU 不接受 `initial_available_stock`。image_ref 省略保留，显式 null 解除绑定并回退主图。
- `SpecSelection = {dimension_ref:EditRef,value_ref:EditRef}`；`EditRef` 只能二选一 `{id:string}` 或 `{client_key:string}`，引用本商品的既有实体或本请求临时键，不能自由引用其他商品。
- 新项必须有 `client_key`，已有项必须有对应 ID，二者不同时提供。`IdMapping = {kind:IMAGE或DIMENSION或VALUE或SKU,client_key:string,id:string}`。临时键用于解决首次保存多规格时尚无数据库 ID 的问题，不持久化为第二套业务身份。

无规格商品提交一个 `spec_values:[]` 的默认 SKU。有规格时每个 SKU 对每个当前维度恰选一值，选项属于对应维度，维度/图片/SKU 同属一个商品；同一商品中完整且启用的组合唯一，历史停用记录允许同组合多代留存。发布后的维度/选项移除若影响在售 SKU，必须在同次请求显式完成停用/替换，不能留下半个有效组合。

上述组合完整性用于发布和已发布商品的有效 SKU。未首次发布的草稿可暂缺维度/选项/组合/价格，但所有已经提供的 ID、临时引用、值类型、商品归属和数量范围仍须合法；不能借“草稿”保存越权引用或负库存。维度名/选项文本的临时空白规则随草稿参数表细化，不能把发布校验整体复用于每次草稿保存。

编辑回显将当前 `dimensions` 与只读 `historical_dimensions` 分开，停用 SKU 引用的旧维度/值可在后者追溯；当前/历史集合不重叠。移出当前定义前须先停用所有依赖它的有效 SKU，可在同次请求完成。数据库如何标识当前定义与历史定义仍是 P040 发现的物理模型缺口，需在生成迁移前选定状态/版本或等效关联表达，不把本响应字段自动视作已有 SQL 列。

同组合再售可把含义未变的历史定义重新纳入当前集合；旧 SKU 的引用仍可通过当前/历史定义并集解析，不能为了分组而删除或改写旧值。集合如何持久表达仍待物理设计，D062 确认的是再售行为及启用组合唯一性。

G05 首次发布写 `published_at`，以后重新上架不改时间。G06 自主下架保留 SKU/库存和历史订单；买家行为按 D058。平台限制时 G05 拒绝；解除限制由平台执行，也不自动上架草稿或商家已下架商品。

G07 建议上限 50 项，非空且 product_id 不重复；整体参数不合法返回 400。合法批量请求返回 200，各件独立事务，`results:[{id,success,data,error}]` 按输入顺序返回；成功项不回滚，失败项只报对当前调用者安全的原因。重新提交失败项应使用新批次键及刷新后的令牌，原批次键重试仍返回原结果。

按既有批量交互，批量 PUBLISH 用于已发布且 OFF_SALE 的重新上架；DRAFT 提示单独进入编辑发布，已在目标状态也作为未处理项返回 INVALID_STATE。单件 G05 则可完成草稿的首次发布，不能把两种入口混成“批量无条件发布所有草稿”。

G09 把“当前可售数量”设置为目标值，`reserved_stock` 不可写；事务先验证令牌和库存真实值，再同步更新与记录前后数量、原因、操作者和时间。冲突则不调整、不写成功记录。这里的令牌方案仍为 P039 建议，不表示已经选定乐观锁实现。

## 8. 购物车与收货地址

### 8.1 购物车

| 编号 | 方法与路径 | 权限 / 防重 | 请求字段 | 成功数据 | 主要表 |
| --- | --- | --- | --- | --- | --- |
| C01 | `GET /api/v1/me/cart` | 用户 / — | 无 | `CartView` | `cart_items → skus → products → stores`，加库存和图片 |
| C02 | `POST /api/v1/me/cart/items` | 用户 / K | `sku_id, quantity` | `CartItem`，新增 201、合并 200 | `cart_items` 及当前 SKU/商品/店铺/库存 |
| C03 | `PATCH /api/v1/me/cart/items/{item_id}` | 本人 / K | `quantity, expected_quantity` | `CartItem` | `cart_items` 及当前可买性 |
| C04 | `DELETE /api/v1/me/cart/items/{item_id}` | 本人 / K | 无 | `CartDeletion` | `cart_items, idempotency_records` |
| C05 | `POST /api/v1/me/cart/items/batch-delete` | 本人 / K | `item_ids`，建议 1–50 个不重复 ID | `CartDeletion` | `cart_items, idempotency_records` |
| C06 | `POST /api/v1/me/cart/restorations` | 本人 / K | `restore_token` | `{items:CartItem[]}` | `cart_items, idempotency_records` 及 SKU 归属校验 |

`C01` 查当前身份的所有商品项，服务端按店铺分组；用户无商品项返回空数组。无 `cart_id`，注册不用初始化任何购物车记录。`selected` 不作为持久列：首版勾选由前端维护，结算预览明确传选中 item_id，由后端重算金额。

C02 同用户同 SKU 合并数量，提交量是本次增量；防重键重试不能再次累加。并发合并依赖唯一约束及事务，不能先查再无条件插入。新增/合并校验当前资格及最终数量不超过当前可售库存；加购不占库存，之后库存变化仍可能导致不足。C03 设置绝对数量，以 `expected_quantity` 识别另一页面期间修改，冲突用 `CART_CHANGED`，不静默截断数量。失效项可删除，但不能通过改数量恢复可售状态。

D062 已确认连续输入协议：前端按 item_id 最多保留一个修改请求在途，同时记录最后服务端确认数量和用户最新目标。请求未完成期间，连续点击只更新本地目标，不并发发送多个旧 expected_quantity；响应成功后若最新目标不同，再用新确认值提交下一次 C03。不同商品项独立处理，不锁整个购物车，固定 300ms 防抖不是必需条件。

示例：已确认 1 → 提交 quantity=2/expected_quantity=1 → 在途期间本地目标变为 3 → 收到确认 2 → 提交 quantity=3/expected_quantity=2。请求结果不确定先用原幂等键恢复，再处理最新目标；第二次不同请求使用新键。真实跨页面冲突仍返回 CART_CHANGED，重新读取后协调用户意图，不静默强行覆盖。前端保存、结算或删除该行前须协调待处理目标，不能拿尚未被服务端确认的数量当已完成数据；删除成功后不再对旧 item_id 补发数量请求。

购物车项显示与跳转按以下规则，店铺本身不可见时移除对应公开跳转目标：

| `purchase_status` 候选 | `purchasable` | 页面文案 | `navigation` |
| --- | --- | --- | --- |
| `AVAILABLE` | true | 正常 | `PRODUCT`，进入商品详情 |
| `INSUFFICIENT_STOCK` | false | 库存不足，最多可选 N 件 | `PRODUCT`；用户可明确调低数量 |
| `SOLD_OUT` | false | 已售罄 | `PRODUCT`，零库存禁购 |
| `SPEC_DISABLED` | false | 所选商品不能购买，商品图变灰 | `STORE`，进入原店铺，不换新规格 |
| `PRODUCT_OFF_SALE` | false | 商品已下架 | `OFF_SALE_PRODUCT`，仅满足 D058 公开条件时进入下架状态页 |
| `NOT_AVAILABLE` | false | 当前商品无法购买 | `NONE`，不泄露平台或店铺内部限制 |

状态优先级建议：平台/店铺不可见 → 商家整款下架 → SKU 停用 → 零库存 → 数量超库存 → 可买。实际购物车保留旧组合，图片是否变灰由 `image_disabled` 表达。不能把已有订单快照规则套用到购物车：可买项价格读取当前 SKU，失效项无法公开的价格置 `null`，不伪造 0 元价。购物车里的旧标题/规格属于有归属的私有查询，不允许公开批量 SKU 接口据此泄露。

C04/C05 支持既有 8 秒撤销交互。`CartDeletion = {deleted_item_ids:string[],restore_token:string,undo_expires_at:datetime}`，token 绑定当前用户、本次删除及原 SKU/数量；它是新提出的契约方案，不增加购物车主表。C05 建议整批归属校验通过后原子删除，不能删除别人商品项或部分成功后又声称整批失败。

C06 在有效期内恢复原 SKU/数量；若同 SKU 又被加入，则合并数量并重算当前状态，不用新 SKU 替代。恢复本身允许保留已失效的原选择，但禁购规则照常返回。token 只能产生一次恢复效果，即使用不同客户端键重复提交也不能再累加：建议把删除操作 ID 用作服务端防重范围中的一次性恢复键，并用条件写保障；不只依靠客户端键。过期返回 `RESTORE_EXPIRED`。token 的签名/存储及清理方式待工程选定，不能把示例 token 当可用凭证。

## 9. 结算预览、提交与拆单

| 编号 | 方法与路径 | 权限 / 防重 | 请求字段 | 成功数据 | 主要表 |
| --- | --- | --- | --- | --- | --- |
| T01 | `POST /api/v1/me/checkout/preview` | 用户 / —，只读 | `CheckoutPreviewRequest` | `CheckoutPreview` | 本人购物车/地址、商品、SKU、店铺、库存 |
| T02 | `POST /api/v1/me/payment-groups` | 用户 / K | `preview_token` | `PaymentGroup`，201 | `payment_groups, shop_orders, order_items, inventory_reservations, sku_inventory`；所选购物车项；防重 |

预览请求二选一：

```json
{
  "source": "CART",
  "cart_item_ids": ["cart_item_keyboard", "cart_item_lamp"],
  "address_id": "address_demo"
}
```

```json
{
  "source": "DIRECT",
  "items": [{"sku_id": "sku_lamp_white_usb", "quantity": 1}],
  "address_id": "address_demo"
}
```

`CART` 必须非空且不重复，不能同时给 `items`；`DIRECT` 首版对应“立即购买”，只允许一个 SKU，不同时给 `cart_item_ids`。地址必须本人所有。预览校验每项当前资格和数量，按实际 SKU 报价分店汇总；任一不可买返回错误，不自动跳过失效项替买家决定购买内容，也不占库存、不生成订单。

`CheckoutPreview` 返回选中行、各店金额、地址内容、总金额、`checked_at` 及不透明 `preview_token / preview_expires_at`。建议 token 绑定当前用户、来源、SKU/数量/实际报价、选中购物车项和地址内容摘要，避免客户端改价；签名/服务端保存方式及有效期仍待定，不为此自动新增业务表。

同一份预览还须有服务端唯一身份，一次成功提交后绑定唯一 payment_group_id。不能只防“相同 Idempotency-Key”：即使换键重复提交同一预览，仍返回原支付单，不能第二次占库存或创建新单；两个并发提交只能一个首次成功。候选复用 idempotency_records 的受控操作范围及预览唯一键记录该绑定，不自动新增业务表；绑定和订单事务一致提交，回滚不消耗预览。已绑定结果的查询优先于预览到期校验，但须先认证和检查归属；原单已付款/关闭也不会凭旧预览再创建一次订单，重新购买须重新预览。

T02 不接受客户端总金额、店铺 ID、成交单价或订单状态；服务端验证 token 后重新校验价格、地址、购物车版本/数量、商品资格和库存。价格变化无论涨跌均返回 `PRICE_CHANGED` 要求重新预览；地址内容变化用 `ADDRESS_CHANGED`，选中项删除/改数量用 `CART_CHANGED`。错误可返回已授权项的当前安全报价，但不自动提交更贵或不同内容的订单。

结算错误 details 建议采用 `{requires_new_preview:true,issues:CheckoutIssue[]}`。每个问题仅引用本次本人已选项，`CheckoutIssue` 含 `code,sku_id?,cart_item_id?,quoted_unit_price?,current_unit_price?,available_stock?`，金额/库存无法继续授权公开时省略对应数据；地址问题不返回其他人的地址。无论返回一个或多个问题，提交失败均无新订单或新库存占用，不能让前端误认为未报错行已成交。

```json
{
  "code": "PRICE_CHANGED",
  "message": "所选商品价格已变化，请重新确认订单。",
  "data": null,
  "request_id": "request_demo_price_changed",
  "field_errors": [],
  "details": {
    "requires_new_preview": true,
    "issues": [
      {
        "code": "PRICE_CHANGED",
        "sku_id": "sku_lamp_white_usb",
        "quoted_unit_price": 5900,
        "current_unit_price": 6900
      }
```

全部校验通过后一次事务完成：

1. 从可售库存转为占用；任何 SKU 不足则整次失败。
2. 创建一个支付单、按店铺拆出的订单、成交及收货快照、每条明细的占用记录。
3. 对 `CART` 来源移除本次已成功提交且一致的选中项，保留未选项；并发变化须检测，不能误删后来新增的数量。`DIRECT` 不改购物车。
4. 保存防重结果并提交；通知如同库同步生成也须一致，异步可靠投递方式后定。

订单创建后才进入待付款，`expires_at` 是实际支付截止时间；建议 15 分钟仍待最终确认。预览期限不是付款期限。取消订单不自动回填购物车，是否重新加购由用户后续操作。

## 10. 模拟付款、取消与订单履约

| 编号 | 方法与路径 | 权限 / 防重 | 请求字段 | 成功数据 | 主要表 |

T04 只取消整次待支付结算，关闭全部关联店铺订单，每条 `RESERVED` 只释放一次；不提供店铺子订单单独取消接口。已支付拒绝取消；重试已完成的同次取消返回原结果。超时关单由服务端内部任务执行，不开放“前端决定已超时”接口，截止时间由后端判断。

T05 只能在明确启用的模拟支付环境运行，没有真实资金交易。客户端不传 `paid=true`、实付金额、交易成功状态或第三方 event_key；服务端在验证归属、截止时间和支付单状态后生成可信模拟事件并去重。模拟失败/服务暂不可用不标记已付款；买家查询原支付单再决定重试。故障注入入口仅用于测试环境，不作为正式商城业务参数。

`expires_at` 到期后，即使内部关单任务还没完成落库，付款接口也必须拒绝；查询返回的 `allowed_actions` 不再允许付款，前端倒计时只作展示，不能决定交易有效期。

支付单响应增加本次服务端 `checked_at`，前端据此估算剩余时间，不假定买家电脑时钟准确；每次查询重新生成，幂等重放后的旧时间须通过 T03 刷新。它是响应时间信息，不新增支付单持久字段。

付款与取消/超时对同一支付单串行化竞争，成功付款时把占用从 `RESERVED` 转 `CONFIRMED`，减少 `reserved_stock`，不再扣第二次 `available_stock`；关闭则转 `RELEASED` 并恢复可售。失败分支不能留下半付款、半关单或部分库存效果。已生成且未过期的订单即使商品后来下架或店铺停用，仍按既有规则允许付款并履约；不重新按当前货架资格否决该历史订单。

O01 按店铺订单展示，返回支付单 ID 便于待付款跳到统一支付页。O02 的商品、规格、图片、单价和收货信息均以快照为准；当前商品变化不重写历史。O03 仅 `PENDING_RECEIPT` 可推进完成。F03 仅已付款的 `PENDING_SHIPMENT` 整店订单可发货，一次填写一个物流承运方和单号，不支持部分发货/多包裹；已有发货不能通过重复请求改为另一物流单。

F01 的 keyword 搜索订单明细中的成交标题快照，不从当前商品标题反推历史；order_no 查询业务订单号，排序建议创建时间倒序并以 ID 保持同值稳定。

商家详情只给本店订单及必要收货快照，不返回同支付单其他店铺明细、全单买家地址簿或其他店铺金额。买家/商家订单响应中的 `allowed_actions` 由服务端当前身份和状态计算；按钮展示不替代动作接口鉴权。首版无已支付取消或退款动作。

日期区间统一建议左闭右开 `[from,to)`，使用带时区时间；结束不大于开始返回参数错误。管理员申请列表默认只显示已提交申请，不展示买家尚未提交的私有草稿；P03 对从未提交的草稿返回不可审核/不可见响应，具体用统一 404。驳回重填后的当前草稿不得替代审核历史中的提交快照。

P14 的默认 `status` 建议 `ACTIVE`、`sort_order` 建议 0，均属参数候选。P15 不允许把分类的父节点设为自己或后代；分类停用对已有商品的处理仍需明确。临时建议停用已被正常在售商品/有效子分类使用的分类时返回 `INVALID_STATE`，先迁移关联或处理子类；不隐式下架大量商品。保留引用，不提供物理删除接口。

P16/P17 是只读查询，不允许管理员改成交金额、替买家确认收货、代商家发货或执行真实退款。管理员列表只返回完成查询所需摘要，详情中的收件资料按管理权限最小展示，不返回整个用户地址簿。

P18 建议返回 `pending_application_count, active_store_count, on_sale_product_count, paid_shop_order_count, paid_amount, currency, checked_at`。支付金额从支付单 `PAID` 汇总，不能 JOIN 多个店铺订单后重复累计；数字由真实演示数据库计算，不预填“热销”数据。指标统计期限本稿建议为全部数据，若加入时间筛选须同步定义口径。

消息导航还须区分买家和商家订单：同一个账号可能兼具两种身份，只有 ORDER 加一个订单 ID 无法确定应进入哪个工作区。Navigation 增加受控 scope，买家发货消息用 BUYER，商家新订单消息用 MERCHANT，申请进度用 MERCHANT；客户端映射固定站内路由，目标 API 再校验归属。scope 可由受控 target_type/事件类型推导，不自动新增数据库列。

反馈内容非空，长度上限后定；返回提交成功及 PENDING 状态，不伪装成客服即时回复。本稿不新增客服会话、反馈处理工作台或通用通知发送接口。

## 14. 状态与事务核对

| 对象 | 当前状态 → 动作 → 结果 | 不允许的绕过 |
| --- | --- | --- |
| 开店申请 | DRAFT/REJECTED → 提交 → PENDING；PENDING → 审核 → APPROVED/REJECTED | 申请人不能审批；审核不能针对已经变化的提交版本 |
| 店铺 | ACTIVE ↔ 管理员停用/恢复 ↔ DISABLED | 停用不删除店主、不增加开店额度；不能阻止合法历史履约 |
| 商品销售 | DRAFT/OFF_SALE → 校验发布 → ON_SALE；ON_SALE → 自主下架 → OFF_SALE | 保存草稿不等于发布；上新时间不因编辑/重上架重置 |
| 平台商品限制 | NORMAL ↔ 平台限制/解除 ↔ RESTRICTED | 商家不能写平台状态；解除不改商家销售意愿 |
| SKU | ENABLED → 替换/停用 → DISABLED；组合再售创建新 ID | D062：同商品启用组合唯一，停用历史可多代同组合；旧 SKU/购物车不自动恢复或改绑 |
| 支付单 | PENDING → 模拟付款 → PAID；PENDING → 取消/超时 → CLOSED | PAID/CLOSED 不能互转；一次跨店结算不能部分付款/部分取消 |
| 店铺订单 | PENDING_PAYMENT → 付款 → PENDING_SHIPMENT → 发货 → PENDING_RECEIPT → 收货 → COMPLETED；未付款关闭 → CLOSED | 商家不能改价；买家不能确认尚未发货的订单；无已支付退款流程 |
| 库存占用 | RESERVED → 付款确认 → CONFIRMED；或 RESERVED → 关单释放 → RELEASED | 确认和释放互斥，只执行一次，不重复扣减可售 |

重点事务：审批＋创建店铺＋绑定店主；替换旧 SKU＋新建组合；人工库存更新＋调整记录；订单创建＋拆单快照＋库存占用＋所选购物车移除；付款状态＋各店待发货＋占用确认；关单状态＋各店关闭＋库存释放；平台状态＋操作历史。具体锁、唯一约束和失败恢复随数据库选型落实，不能只依靠页面按钮禁用。

### 18.1 结论对照

| 项目 | 判断 | 当前处理 |
| --- | --- | --- |
| 1. 已支付无法履约的兜底 | 真实运营需要处理，但不是数据库并发死锁；首版明确采用模拟交易、不做退款。店铺停用不禁止已有订单履约这一前提已在第 2/10 节规定 | 首版保留明确范围限制；若用户要求异常履约闭环，再评审按店铺订单处理的补偿/退款及库存、金额、审计一致性，不能简单强制 CLOSED |
| 2. 发货后自动完成 | 是可选生命周期规则，缺少它不等于现有人工确认流程出错；长期 PENDING_RECEIPT 是未完成状态 | 可候选加入内部超时确认任务，期限和起算点待定，不新增买家调用的“自动收货”接口；不把发货或计时结束伪称真实签收 |

| 4. 连点购物车数量 | 存在乱序请求问题，单独 300ms 防抖不保证前一请求完成 | D062 已确认每商品项单请求在途＋合并最新目标，保留绝对目标和冲突校验，防抖仅可选 |
| 5. 轻量付款轮询 | T03 返回 PaymentOrderLink 摘要，没有各店 OrderLine；当前模拟付款也不要求固定每 1.5 秒长期轮询，尚无证据认定性能瓶颈 | 先复用 T05 返回值及 T03 结果查询，等待时有界退避、终态/页面离开停止；以后有真实异步支付或测得需要，再评审字段投影/轻量子资源 |

| 8. 配送范围错误 | 当前只有模拟物流与统一演示包邮，没有商家配送区域规则，不能凭包邮推断真实全区域可送，也不能加一个没有触发依据的错误码充数 | 首版建议明确为不校验真实物流可达性的演示规则；如纳入区域限制，再一起定义范围数据、逐店校验、预览/提交重校验及错误码 |

### 18.2 已付款终止与自动完成的边界

真实的永久无法履约需要异常处理，这一点成立；当前没有平台强制关单接口是已声明的演示范围取舍。仅把已付订单状态改为 CLOSED 不能代表买家已退款；此时库存占用已经 CONFIRMED，不能再调用待付款的 RELEASED 分支。若货物已损毁，更不能无条件恢复为可售库存。跨店付款中只有一家无法履约时，还涉及店铺订单、原支付总额及部分补偿/退款的对应关系。

因此新增这类能力需一起评审异常原因、资金/模拟资金结果、逐店状态、库存是否恢复、操作权限、重复请求和审计；不能用“平台兜底”绕过这些设计。原有店铺停用仍保留历史履约权限，不因本节改变。

自动收货若采纳，需确定是从 shipped_at 起算还是另有可信签收依据、截止时间如何保存、系统操作者/完成来源如何追溯、重启补扫及与 O03 手动确认竞争时仅完成一次。7 天或 14 天只是第三方举例，本轮不定期限，不把买家未登录当成实际已收到货物的事实。

### 18.3 同组合再售的建议表达

以旧 SKU A 为“白色 M”、替换后已停用为例：原购物车继续引用 A，保持“所选商品不能购买”。D062 确认再次售卖白色 M 时新建 SKU B，复用合法的规格值定义但采用新的 SKU ID，旧购物车不自动改绑 B。新库存/售价由商家确认，不自动从旧 SKU 复制可售库存或占用记录。

唯一性目标已调整为“同一商品中，启用的相同完整组合至多一条”；历史停用记录可保留相同 spec_key。具体唯一约束依数据库产品选定后实现，不能用无条件 (product_id,spec_key) 或 (product_id,spec_key,status) 唯一键阻止多条相同停用历史。D062 替换 G04 的历史重复即冲突占位，SKU_COMBINATION_CONFLICT 仅用于启用组合冲突等真正非法重复；D057 的旧选择失效行为不变。

暂时断货优先把现有 SKU 可售库存设为 0，显示售罄；补货仍用原 SKU，和已经替换/退役的组合再售区分。直接恢复旧 ID 是否属于另一种业务意图需另行明确，不能为解决再售而无意恢复所有旧购物车。

### 18.4 连续数量输入与会话恢复

购物车按 D062 以 item_id 管理单项请求队列：已确认数量 1，用户点到 2 后提交 quantity=2、expected_quantity=1；请求未完成期间再点到 3，只更新本地目标为 3。拿到服务器确认 2 后，再发 quantity=3、expected_quantity=2。其他商品项可独立操作，不锁住整个购物车。

不确定的超时先用原防重键恢复首次请求结果，再处理最新目标；其他页面实际改动时的 CART_CHANGED 仍须重新读取并协调用户意图，不静默覆盖。固定防抖不能替代在途串行；增量 delta 也需要幂等、范围校验和异常恢复，并非天然没有并发问题。

认证过期时按 D062 暂停受保护的写入，保留当前账号名下当前页面内存表单，以共用登录视图和可恢复的站内流程认证；只有原账号恢复后才允许继续。换账号要清除原账号私有表单，不能自动以新身份提交旧资料。重新认证后重新读取权限、编辑令牌和库存，冲突要提示合并/重载，不直接重放下单或付款。

续期可降低打断频率，但无法覆盖撤权、主动退出、会话失效等全部情况。是否滑动续期、是否采用 refresh、绝对/空闲期限和写请求防护待认证方案一起定。上述内存保留建议不修改 D055 的“未保存输入不承诺跨刷新恢复”，已保存草稿仍按服务端数据回显。

### 18.5 素材回收的必要检查

不能仅因素材未出现在当前在售商品图集就删除。D062 确认核查范围至少包括头像、申请草稿及每次提交快照中的 Logo、正式店铺 Logo、商品草稿/下架商品图集、SKU 图片关联及订单成交图片快照；这些引用中任一仍需保留即可阻止回收。已上传未绑定但仍供当前编辑使用的素材须有宽限期，具体期限待确认。

清理前受控标记待删除资格，并使绑定操作与清理标记在同一素材记录上协调；绑定时验证仍可用，清理时再次核查无引用，防止“扫描无引用之后刚被保存”却被删掉。对象存储删除失败须可重试，不能只删元数据而永久遗留对象，也不能覆盖被历史订单使用的对象。可复用 media_assets.status 等候选能力，最终物理方案另定；不因为确认回收行为就提前搭建消息队列或额外服务。

上传大小/频率/用户存储配额也应随工程确定，清理不是允许无限上传的替代措施。实际 ref_count 只有在全部绑定、解绑、快照创建和回收都可靠维护时才能用作依据；本项目首版未选定该计数列。

### 18.6 采纳状态与验证边界

四项完善已由 D062 采纳并同步正文。已付款异常终止、自动完成不在本轮新增范围；轻量付款状态接口、refresh 及配送错误码不提前新增，相关需求后续再评审。

本节确认的是四项行为及对应约束目标，不代表其他接口/物理字段/技术方案被整体采纳，更不表示已实现任务或服务。本轮同步正文、数据库唯一性/引用策略及待执行验收；没有做性能测量、真实支付/物流验证、存储回收或并发测试。
